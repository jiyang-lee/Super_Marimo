# 베타 버전으로 가는 길

## 1. 전체 구조를 “프론트 중심”이 아니라 “디바이스 이벤트 중심”으로 정리

현재 목표 구조는 이렇게 봐야 한다.

```
RP2040 마이크
→ 호출어 감지
→ 음성 입력/STT
→ API Server
→ LLM Server
→ TTS
→ 스피커 출력

Wemos 거리센서
→ 가까운 사람 감지
→ API Server
→ LLM Server
→ TTS
→ 스피커 출력
```

프론트는 메인 입력 장치가 아니라 **상태 확인, 로그 확인, 수동 테스트, 설정 변경용 UI**에 가깝다.

따라서 백엔드 문서와 API 이름도 “사용자가 프론트에서 파일을 업로드한다”가 아니라 “센서/마이크 이벤트가 들어오면 서버가 반응한다”는 방향으로 바꾸는 게 맞다.

---

## 2. Voice 서버를 “파일 업로드 서버”가 아니라 “음성 처리 서버”로 정의

현재 Voice 서버의 역할은 STT/TTS 처리다.

다만 실제 시스템에서는 프론트가 오디오 파일을 올리는 게 핵심이 아니다.

Voice 서버는 다음 역할로 정의하는 게 좋다.

```
Voice Server
= RP2040 또는 오디오 입력 장치에서 들어온 음성 신호를 텍스트로 바꾸고,
= LLM 응답 텍스트를 음성으로 바꾸는 음성 처리 전용 서버
```

즉, 문서에서 “오디오 파일 업로드”라는 표현은 줄이고, **음성 입력 처리**, **STT 처리**, **TTS 출력 생성**으로 표현하는 게 더 정확하다.

---

## 3. RP2040 마이크 흐름을 별도 서비스로 분리

현재 큰 빈칸은 **RP2040 마이크를 누가 계속 듣고 있을 것인가**야.

API 서버는 HTTP 요청을 받는 서버이고, 항상 마이크를 감시하는 역할에는 적합하지 않다.

따라서 별도 프로세스 또는 서비스가 필요하다.

추천 이름은 다음 중 하나다.

```
mic-listener
wakeword-listener
device-agent
voice-agent
```

역할은 다음과 같다.

```
1. RP2040 마이크 입력을 지속적으로 수신
2. 호출어 감지
3. 호출어 감지 후 실제 발화 구간 수집
4. STT 요청
5. API Server에 텍스트 질문 전달
6. 응답을 TTS로 변환
7. 스피커로 출력
```

이 서비스는 `marimo_server` 쪽에 두는 게 자연스럽다.

왜냐하면 마이크, STT, TTS, 스피커가 음성 처리 장치와 더 가깝기 때문이다.

---

## 4. `/voice/ask`는 유지하되 “텍스트화된 음성 이벤트 처리 API”로 정의

현재 `/voice/ask`는 오디오가 아니라 텍스트를 받는다.

이건 잘못된 게 아니라, 오히려 현재 구조에 맞다.

다만 이름과 설명을 이렇게 명확히 해야 한다.

```
/voice/ask
= 호출어 감지 후 STT가 끝난 텍스트를 API 서버에 전달하는 엔드포인트
= 오디오 파일을 직접 받지 않음
= 음성 이벤트의 대화 결과를 DB에 저장함
```

즉, `/voice/ask`는 “음성 파일 처리 API”가 아니라 **음성에서 나온 텍스트 이벤트를 저장하고 LLM에 연결하는 API**로 보면 된다.

---

## 5. “호출어 감지 이벤트” API를 추가

RP2040 마이크가 항상 켜져 있고 호출어를 감지한다면, 호출어 감지 자체도 이벤트로 남기는 게 좋다.

예를 들어 이런 이벤트가 필요하다.

```
wakeword_detected
speech_started
speech_ended
stt_completed
llm_completed
tts_played
```

추천 API는 다음과 같다.

```
POST /events/wakeword
```

역할은 다음과 같다.

```
1. 호출어 감지 시각 저장
2. 어떤 장치에서 감지됐는지 저장
3. 이후 대화 세션과 연결
4. 디버깅용 로그로 활용
```

이렇게 하면 나중에 “왜 갑자기 마리모가 반응했는지”를 DB에서 추적할 수 있다.

---

## 6. 초음파 거리센서 기반 “선제 인사” 로직 추가

네 프로젝트의 핵심 기능 중 하나는 **사람이 가까이 오면 마리모가 먼저 인사하는 것**이다.

현재 센서 저장은 되어 있지만, “거리값이 가까우면 먼저 말하기” 로직은 별도로 필요하다.

수정 방향은 다음과 같다.

```
Wemos
→ 거리값 전송
→ API Server가 거리 상태 판단
→ 가까움 조건 만족 시 greeting 이벤트 생성
→ LLM Server에 짧은 인사 문장 요청
→ TTS 출력 요청
```

주의할 점은 **쿨다운**이 꼭 필요하다는 것이다.

예를 들어 사람이 계속 앞에 있으면 3초마다 인사를 반복하면 안 된다.

따라서 조건은 이렇게 잡는 게 좋다.

```
거리 10cm 이하 감지
+ 최근 30초 또는 1분 내 인사한 적 없음
= 선제 인사 실행
```

---

## 7. “자동 발화 정책” 테이블 또는 로그 추가

자동 인사, 호출어 반응, 센서 경고 발화는 모두 시스템이 먼저 말하는 기능이다.

이 기능은 반드시 기록이 필요하다.

추가하면 좋은 로그 항목은 다음과 같다.

```
event_type
device_id
trigger_source
sensor_snapshot
distance
state_level
generated_text
played
created_at
```

예시 이벤트 타입은 다음과 같다.

```
wakeword
proactive_greeting
sensor_warning
manual_test
```

이걸 기존 `interaction_log`에 넣어도 되고, 별도 `device_event_log` 테이블을 만들어도 된다.

추천은 별도 테이블이다.

```
device_event_log
= 호출어 감지, 거리센서 인사, 자동 발화 같은 장치 이벤트 기록용
```

---

## 8. API 서버가 Voice 서버에 “TTS 요청”을 보낼 수 있게 수정

선제 인사는 사용자가 질문한 게 아니라 시스템이 먼저 말하는 것이다.

따라서 API 서버가 LLM 답변 또는 인사 문장을 만든 뒤, Voice 서버에 TTS를 요청할 수 있어야 한다.

흐름은 다음과 같다.

```
거리센서 가까움 감지
→ API Server가 인사 문장 생성
→ Voice Server에 TTS 요청
→ 스피커 출력 담당 서비스가 재생
```

다만 여기서 중요한 점은 API 서버가 직접 스피커를 제어할지, 아니면 음성 장치 쪽 agent가 스피커를 제어할지를 정해야 한다.

추천은 다음 구조다.

```
API Server
= 말할 문장을 생성하고 기록

Voice Agent
= TTS 생성 요청
= 실제 스피커 재생
```

즉, API 서버는 “무엇을 말할지”를 결정하고, Voice Agent는 “실제로 말하게 하는 것”을 담당한다.

---

## 9. 프론트는 “대화 입력기”보다 “상태 모니터링 UI”로 역할 조정

프론트가 직접 오디오를 업로드하는 구조가 아니라면, 프론트 역할도 바뀐다.

프론트는 다음 기능이 중심이 된다.

```
현재 센서값 보기
마리모 상태 보기
최근 대화 로그 보기
호출어 감지 로그 보기
자동 인사 로그 보기
수동으로 말 걸기 테스트
STT/TTS 서버 상태 확인
```

즉, 프론트는 메인 음성 입력 장치가 아니라 **시스템 상태판 + 테스트 패널**에 가깝다.

그래도 `/ask`는 남겨두는 게 좋다.

수동 테스트용으로 매우 유용하다.

---

## 10. 최종 목표 흐름을 3개로 나눠 문서화

문서에는 기능별로 흐름을 나눠 적는 게 좋다.

## A. 호출어 기반 대화

```
RP2040 마이크
→ Voice Agent가 호출어 감지
→ 발화 수집
→ STT 처리
→ API Server /voice/ask
→ LLM Server
→ DB 저장
→ TTS 생성
→ 스피커 출력
```

## B. 거리센서 기반 선제 인사

```
Wemos 거리센서
→ API Server /sensor/realtime-ingest
→ 거리값 판단
→ 쿨다운 확인
→ 인사 이벤트 생성
→ LLM 또는 고정 문장 생성
→ TTS 생성
→ 스피커 출력
```

## C. 프론트 수동 테스트

```
Frontend
→ API Server /ask
→ LLM Server
→ DB 저장
→ Frontend에 텍스트 응답
```

이렇게 나누면 프로젝트 설명이 훨씬 정확해진다.

# 최종 요약

수정 방향은 “오디오 파일 업로드 API 추가”가 아니다.

핵심은 이거다.

```
1. RP2040 마이크를 계속 듣는 Voice Agent 필요
2. 호출어 감지 후 STT → /voice/ask로 텍스트 전달
3. 거리센서 가까움 감지 시 API 서버가 선제 인사 이벤트 생성
4. 자동 발화에는 쿨다운 필요
5. API 서버는 DB/LLM/정책 판단 담당
6. Voice Agent는 마이크 감지/STT/TTS/스피커 출력 담당
7. 프론트는 상태 모니터링과 테스트용 UI로 정리
```

따라서 `/voice/stt-ask` 같은 파일 업로드 API는 이번 구조의 핵심이 아니다.

오히려 **`voice-agent` 또는 `mic-listener` 서비스를 추가하는 방향**이 더 맞다.
