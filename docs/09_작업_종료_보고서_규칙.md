# 작업 종료 보고서 규칙

이 문서는 큰 작업이 끝난 뒤 어떤 보고서를 남겨야 하는지 정리한다.

## 1. 언제 쓰는가
- 서버 구조가 바뀌었을 때
- DB 구조가 바뀌었을 때
- API가 추가되거나 바뀌었을 때
- GitHub 브랜치 규칙을 바꿨을 때
- 베타 전환처럼 큰 흐름이 바뀌었을 때

## 2. 반드시 들어갈 내용
- 수정된 다이어그램
- 무엇을 바꿨는지
- 왜 바꿨는지
- 어떻게 확인했는지
- 남은 문제는 무엇인지
- 다음 작업이 무엇인지

## 3. 다이어그램 규칙
- 보고서는 `report/` 아래에 둔다.
- 보고서의 최상단에 수정된 다이어그램을 둔다.
- 서버 구조 변경이면 아키텍처 또는 시퀀스 다이어그램을 넣는다.
- DB 구조 변경이면 테이블 관계 다이어그램을 넣는다.
- 변경 전과 변경 후의 차이가 바로 보이게 쓴다.
- 다이어그램 없이 구조 변경 보고서를 끝내지 않는다.

## 4. 작성 원칙
- 한국어로만 쓴다.
- 길게 쓰기보다 핵심을 먼저 쓴다.
- 코드 설명보다 결과를 적는다.
- 확인하지 않은 내용은 적지 않는다.

## 5. 저장 위치
- 보고서는 `report/` 아래에 둔다.
- 파일명은 작업 순서가 보이게 `00_`, `01_`, `02_` 같은 형식을 유지한다.
- 베타 전환처럼 큰 작업은 별도 파일로 남긴다.

## 6. 추천 구조
```md
# 제목

## 다이어그램
## 요약
## 변경 내용
## 검증 결과
## 남은 이슈
## 다음 단계
```
